# API privada 1.0.0

[OpenAPI procesable](openapi.json). Gateway local: http://localhost:8080. Todos los cuerpos son JSON; se rechazan campos desconocidos y cuerpos mayores de 256 KiB. Las rutas de usuario requieren `Authorization: Bearer ACCESS_TOKEN`; las administrativas requieren además rol ADMINISTRADOR verificado en Usuarios. Credenciales M2M de Clínica no habilitan estas rutas. Cambiar un id ajeno devuelve 404; el rol de administrador no permite leer escenarios ajenos.

## Cuenta

`POST /api/v1/auth/registro` con `{"email":"persona@example.test","password":"contraseña-de-al-menos-12"}` crea USUARIO (201). Login usa el mismo cuerpo (200: accessToken, usuario). No se admite `rol` al registrar. Argon2 id: salt aleatorio 16 bytes, m=19456 KiB, t=2, p=1, hash de 32 bytes; no se persiste contraseña plana. Email normalizado único en MySQL. El administrador inicial se crea una sola vez con email `admin@renewable.local` y ADMIN_PASSWORD de `.env`.

Refresh usa cookie HttpOnly `renewable_refresh`, SameSite Strict, path `/api/v1/auth`, 7 días, rotación en transacción y solo hash del refresh en SQL. Access HS256: audiencia renewable-web, emisor renewable-usuarios, sesión identificada y 15 minutos. Gateway consulta la sesión y rol actual en cada operación privada; logout elimina la sesión y revoca también el access existente. La web no persiste access en localStorage/sessionStorage. Las operaciones auth rechazan Origin de otro host; por HTTPS se debe activar COOKIE_SECURE=true (en local HTTP es false).

`POST /auth/refresh` y `/auth/logout` bajo `/api/v1` no necesitan cuerpo. Logout 204. `GET /perfil` devuelve id/email/rol. `GET /admin/usuarios` lista hasta 100 usuarios y `PUT /admin/usuarios/{id}/rol` con `{"rol":"USUARIO"}` devuelve 204; se impide degradar al último administrador.

## Guardar, confirmar y consultar

1. `POST /api/v1/lugares`: `{"nombre":"Hospital","ubicacion":"Declaración manual","superficieM2":50}`. Devuelve id y version=1. GET lista propios; PUT /lugares/{id} requiere versión actual y permite editar/archivar.
2. `POST /api/v1/configuraciones`: `{"nombre":"Sala","lugarId":"ID_LUGAR","consumo":{"diasPeriodo":30,"equipos":[{"catalogoId":"iluminacion","cantidad":4,"horasPorDia":5,"diasUso":30,"factorFuncionamiento":1}]}}`. Consumo resuelve fichas activas por un único lote y calcula; ignora cualquier resultado del navegador. Conserva fichas/versiones, entrada, lugar y desglose en snapshot. GET lista/abre; PUT requiere version y recalcula explícitamente contra catálogo vigente; /{id}/duplicar crea otra id. Ninguno publica estudio hasta confirmar.
3. `POST /api/v1/configuraciones/{id}/evaluaciones`, cabecera `Idempotency-Key: intento-unico-123`, cuerpo `{"version":1,"versionLugar":1,"solar":{"horasSolPico":4,"factorRendimiento":0.8,"coberturaObjetivo":1}}`. Devuelve 201; repetición exacta devuelve 200 y mismo id. Reutilizar clave con otra entrada: 409. Una evaluación identifica el par versión de configuración/versión del lugar. Confirmar el mismo par con otros parámetros requiere usar la operación de variantes, evitando descartar silenciosamente los cambios.
4. `GET /api/v1/evaluaciones` y /{id} devuelven snapshots inmutables y estudioIds. Publicación PENDIENTE significa que la outbox todavía no recibió confirmación del broker; ENVIADA no implica que el estudio haya terminado. El resultado anterior sigue disponible después de editar lugar, fichas o configuración.
5. `GET /api/v1/estudios?evaluacionId=ID` y /{id} muestran estado durable. Puede recibirse 404 transitorio antes de que el worker cree el documento. Consultar periódicamente; no crear otra evaluación por ese 404. La web consulta cada 5 s. `POST /evaluaciones/{id}/estudios` con otra clave y SolarOptions crea una variante (202); misma clave/opciones devuelve el mismo estudio. No altera el estudio previo.

Los números solares admiten seis decimales: HSP manual 0.5..8, rendimiento 0.1..1, cobertura >0..1 y superficie opcional >0..1.000.000 m². En ausencia de superficie en confirmación se usa la del lugar bloqueado. En variantes se debe enviar la superficie deseada; no se reconsulta ni modifica el snapshot. No hay una fuente de irradiación acordada para ubicaciones reales. Orientación e inclinación no verificadas. Dimensionamiento: promedio diario ≤10^12 kWh y cantidad calculada ≤1.000 millones de paneles, para acotar aritmética y costos; el vendedor simulado tiene límites comerciales mucho menores y puede no ofrecer stock. No se promete autonomía durante cortes.

La transacción local bloquea la configuración y lugar propios, verifica ambas versiones, inserta evaluación, idempotencia y outbox. No espera a RabbitMQ ni hace HTTP bajo esos locks. Revalida las versiones activas del catálogo antes de esa transacción; el snapshot corresponde a esa lectura, sin prometer una transacción distribuida con el catálogo. Ante ficha modificada: 409 y actualización explícita de configuración. Los errores nuevos usan el sobre codigo/mensaje/detalles/traceId; 401 sesión, 403 rol/Origin, 404 propiedad, 409 conflicto, 422 cuerpo/validación, 429 cuota, 503 dependencia. Las rutas privadas usan cuota 5/s, ráfaga 20 por usuario; la cuota M2M permanece 60/min, ráfaga 10.

## Administración

GET/POST `/api/v1/admin/electrodomesticos` y PUT /{id}: ids inmutables, modo POTENCIA (W>0, ciclos=0, factor>0..1) o CICLOS (W=0, energía>0, factor normalizado a 1), fuente, activo y versión esperada al editar. Datos en MySQL y evento en outbox en el mismo commit. GET/POST `/admin/paneles` y PUT /{id}: Mongo, CAS por versión, superficie efectiva en milésimas de m² (`2500` = 2.5 m²), precio en centavos de ARS/USD. Un precio cero es desconocido y obliga al criterio por superficie; no se convierte moneda. Fuente debe identificar una referencia verificable o una simulación. La ficha debe corresponder al SKU comercial para que el proveedor confirme una oferta.

POST `/admin/catalogo/reindexar` reconstruye un índice temporal y lo intercambia al completar las tareas de Meilisearch. GET `/admin/mensajeria` inspecciona principal/retry/DLQ. POST `/admin/mensajeria/reprocesar` con `{"limite":10}` republica solo eventos compatibles con confirmación previa al ACK; conserva los incompatibles en DLQ. No edita cuerpos inválidos automáticamente ni convierte una versión desconocida en válida.

## Ampliación privada 1.1.0 — 2026-11-09

Archivo/restauración: PATCH /api/v1/{lugares|configuraciones}/{id}/archivo con {"version":1,"archivado":true|false}; 204, sin nueva versión de contenido ni recálculo. DELETE /api/v1/{lugares|configuraciones}/{id} con {"version":1}; 204 y eliminación lógica de las listas. Se preservan snapshots/evaluaciones/estudios. Un lugar con consumos, incluidos archivados, devuelve 409 LUGAR_CON_CONSUMOS hasta moverlos o eliminarlos. Mismo control de propietario y versión; los eliminados no se pueden editar, duplicar ni confirmar. PUT sigue siendo edición de contenido. POST /admin/paneles/reindexar solicita resincronización derivada (202). [Detalle de experiencia](../../EXPERIENCIA-CLIENTE.md). El M2M 1.0.1 no cambia.
