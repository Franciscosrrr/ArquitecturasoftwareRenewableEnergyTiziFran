# ADR-012 - D12 - Balanceo

> Vigencia: consultar la [revisión de 2026-11-08](#revision-vigente-20261108). Los estados anteriores se conservan como historia.

Versión 1.0.0 · Entrega 2 · Estado: **Diseño propuesto; no implementado en este hito**. Autores: Tiziano Nicolas y Francisco Skrie. Reemplaza: ninguna.

## Contexto

El arranque de entrega 2 usa una instancia de cada servicio. El balanceo funcional sobre dos o más instancias se exige en la defensa final.

## Decisión

Mantener la propuesta de round-robin explícito en gateway hacia dos instancias Solar saludables. Chequeo cada 5 s, timeout 1 s, retiro tras dos fallos y reincorporación tras dos éxitos. Sin destinos: 503. Las réplicas Solar compartirán su propia MongoDB y usarán reclamo/lease e idempotencia para trabajo durable. No reintentar escrituras sin una garantía de idempotencia.

## Alternativas consideradas

Nginx/HAProxy simplifican operación pero ocultan parte de la decisión a defender; balancear Consumo stateless es posible, pero se eligió Solar por el procesamiento planeado. La decisión debe revalidarse cuando exista Solar real.

## Consecuencias y validación

En entrega 2 no se afirma distribución ni recuperación entre réplicas. La verificación futura debe registrar id de instancia y retirar una de ellas bajo tráfico. Una BD única seguirá siendo un punto de falla.

Las evidencias ejecutadas se enumeran en [DELIVERY-2](../DELIVERY-2.md). Una decisión propuesta no se presenta como una implementación validada.

## Revisión vigente 2026-11-08 - contexto y justificación

**Estado:** Diseño conservado; dos instancias aún no implementadas.

### Contexto vigente

Hoy hay una instancia Solar. Se exige distribuir tráfico entre dos o más y retirar una caída. Las peticiones de cotización son sin sesión/estado local de usuario; circuitos y contadores sí son locales.

### Decisión

Conservar el round-robin previsto en el gateway Go con comprobaciones activas: intervalo 5 s, timeout 1 s, retiro tras dos fallos y reingreso tras dos éxitos, sujeto a prueba. Solar compartirá su propia persistencia cuando exista. No implementar sticky sessions para el borrador invitado.

### Por qué se elige para este proyecto

La clase usa NGINX y explica round-robin/stateless/healthchecks. Mantener un componente de entrada ya existente permite propagar el mismo deadline, correlación y respuesta de error sin sumar otro proxy a esta demo. La ventaja es de integración y operación en este proyecto, no de rendimiento sobre NGINX.

### Alternativas y comparación con clase

NGINX/HAProxy serían preferibles para funciones de proxy y operación maduras; un balanceador propio requiere programar y probar selección, concurrencia y disponibilidad. Least-connections puede servir si tareas tienen duraciones dispares; round-robin presupone réplicas similares.

### Consecuencias, límites y evidencia

No se presenta el proxy actual de destino único como balanceo implementado. Faltan pruebas con id de instancia, reparto, retiro/reingreso y cuotas compartidas. MongoDB/MySQL únicos y gateway único seguirán limitando disponibilidad.

### Material que sustenta la decisión

Clase 8.pdf pp. 3-9; Clase 7.pdf pp. 8-15.

**Qué cambió y por qué:** se explicitan contexto, criterio de elección y relación con los PDF prácticos a pedido del equipo; se conserva la tecnología/estilo previo y se distingue implementación de diseño pendiente. Las revisiones futuras se añaden a este mismo ADR, sin archivo de reemplazo.

## Actualización 2026-11-09 — Dos Solar balanceados con health checks activos

### Contexto y qué cambió

Gateway selecciona round-robin entre Solar 1/2, con checks cada 5 s y timeout1s, retiro tras2fallos y reintegro tras2éxitos. Expone estado por destino y contador de distribución; no reenvía automáticamente un POST fallido a otra réplica. Mongo y broker compartidos con ownership/deduplicación.

### Decisión y por qué

Demuestra distribución y supervivencia de una réplica. Conservar gateway Go evita sumar NGINX para esta escala y facilita verificar límites/correlación, aceptando mantener el proxy propio. Gateway/bases/broker siguen siendo puntos únicos locales.

### Alternativas de clase y consecuencias

Clase8 usa NGINX; se preserva Go por integración, sin afirmar mayor madurez o capacidad que NGINX/HAProxy.
