# ADR-003 — Persistencia por patrones de acceso

Decisión del enunciado: D3. Versión: 1.0.0. Estado: **Propuesto; versión inicial requerida**. Reemplaza: ninguna. Autores: Tiziano Nicolas (2407889) y Francisco Skrie (2423159).

## Contexto

Usuarios, configuraciones e idempotencia necesitan integridad y transacciones. Solar lee/escribe estudios completos con entradas, candidatos y resultados. Se exigen datos relacionales y no relacionales.

## Decisión

MySQL Community/InnoDB independiente para Usuarios, Electrodomésticos y Consumo; MongoDB Community para Solar. Volúmenes persistentes. Meilisearch y Valkey son proyección/caché de Electrodomésticos, no fuentes principales.

## Alternativas consideradas

MySQL en todo con JSON es viable para agregados pero no muestra un segundo almacén principal del dominio. MongoDB en todo dificulta justificar relaciones/transacciones relacionales. SaaS administrado pago queda excluido.

## Consecuencias y límites

Dos motores y más contenedores, con migraciones/semillas propias. MySQL posee restricciones locales; MongoDB usa clave única y transiciones atómicas por estudio. Inicialmente no se requieren transacciones multidocumento Solar. Sin replicación de bases hay puntos de falla.

## Validación y evolución

Integración contra ambas bases, evaluación/outbox atómicas, duplicados Solar, persistencia al reiniciar y recuperación de volúmenes. Revisar D3 con datos y carga en entrega 2.
