# ADR-001 — Límites de servicios y propiedad de datos

Decisión del enunciado: D1. Versión: 1.0.0. Estado: **Adoptado como diseño de entrega 1; validación productiva pendiente**. Reemplaza: ninguna. Autores: Tiziano Nicolas (2407889) y Francisco Skrie (2423159).

## Contexto

El flujo exige identidad, catálogo energético, guardados/evaluaciones y selección solar. El usuario requiere BD propia por servicio y el TP al menos tres servicios.

## Decisión

Cuatro servicios: Usuarios, Electrodomésticos, Consumo y Solar. Usuarios/catálogos/guardados permanecen separados. Cada uno es el único dueño de su base; las referencias externas se validan por API o eventos. Se conservan snapshots/versiones para historial reproducible.

## Alternativas consideradas

Tres servicios mezclando identidad con Consumo: menos despliegues pero responsabilidades y permisos más acoplados. Catálogo único de todos los equipos/paneles: limita independencia del motor solar. Una BD compartida con acceso cruzado: simplifica JOIN pero rompe ownership.

## Consecuencias y límites

Se aceptan cuatro despliegues y composición distribuida; no hay FK/JOIN entre bases. Las réplicas de Solar comparten solar_db dentro del mismo servicio. La futura asignación externa puede revisar el servicio responsable de integrar al proveedor.

## Validación y evolución

Verificar credenciales/redes y ausencia de acceso cruzado; demostrar registro, guardado/evaluación y recomendación. La separación no está implementada aún.

Si cambia esta decisión, conservar este ADR como reemplazado y crear otro con vínculo al anterior. Ver [arquitectura](../ARCHITECTURE.md) y [alcance](../../SPEC.md).

## Aclaración de alcance: invitado

La identidad es opcional para usar la calculadora. Consumo y Solar también ofrecen casos temporales sin persistencia, manteniendo límites/BD propios y el flujo durable autenticado. No se agrega un servicio ni se comparte almacenamiento. Ver [ADR complementario](ADR-GUEST.md).
