## Historia conservada: registro inicial

> Estado histórico: reemplazado para el alcance de entrega 2 por [ADR-002-E2](ADR-002.md#evolucion-entrega-2). Se conserva el texto original como antecedente.
Decisión del enunciado: D2. Versión: 1.0.0. Estado: **Propuesto; complemento anticipado**. Reemplaza: ninguna. Autores: Tiziano Nicolas (2407889) y Francisco Skrie (2423159).

#### Contexto

El usuario conoce Go y las clases muestran Go/Gin/GORM. Se necesitan dos estilos distinguibles y Solar contiene integraciones/reglas más variables.

#### Decisión

Go/Gin en servicios y gateway. Capas para Usuarios, Electrodomésticos y Consumo; hexagonal en Solar con puertos definidos por el núcleo y adaptadores externos. React/JavaScript en frontend.

#### Alternativas consideradas

Java/Spring exige aprendizaje no deseado. JavaScript/Fastify es viable pero Go se corresponde con los ejemplos de clase. Hexagonal en todo suma mapeos donde capas basta.

#### Consecuencias y límites

Tecnología común y Go conocido; interfaces/mapeos útiles en Solar. El framework no define el estilo. No se añade Event Sourcing ni CQRS global por tener eventos o un índice.

#### Validación y evolución

Revisar dirección de imports y que el dominio Solar no dependa de Gin/driver/SDK; probar reglas con adaptadores falsos y conexiones reales aparte.

Si cambia esta decisión, conservar este ADR como reemplazado y crear otro con vínculo al anterior. Ver [arquitectura](../ARCHITECTURE.md) y [alcance](../../SPEC.md).

## Historia conservada: evolución de Entrega 2

Procedencia: ADR-002-E2.md. Consolidado el 2026-11-08 sin descartar su contenido.

### ADR-002-E2 - Validación de D2 en el flujo operativo

Estado: adoptado y comprobado localmente. Reemplaza ADR-002 para el alcance de entrega 2; se conserva su historia.

#### Contexto

ADR-002 propuso Go/Gin, capas para Usuarios, Electrodomésticos y Consumo, y hexagonal para Solar. La segunda entrega necesita transformar parte de esa propuesta en código real.

#### Decisión

Implementar gateway/Consumo/Electrodomésticos con Gin. Consumo concentra reglas decimales y validación del caso en application; HTTP solo adapta, autentica y responde. El cliente de catálogo se inyecta por una interfaz propia de application. El repositorio SQL pertenece exclusivamente a Electrodomésticos. Las lecturas simples del catálogo usan HTTP → repository; no se añade una capa de aplicación vacía. React/JavaScript para el flujo temporal. platform comparte solo infraestructura técnica.

#### Alternativas y consecuencias

Duplicar fórmulas en web/M2M produce divergencias; ambas rutas y la simulación por catálogo usan Calculate. Importar tablas/entidades de otro servicio viola límites; se usa un DTO local del contrato. Una capa sin comportamiento propio solo agrega indirección. Solar hexagonal se mantiene como diseño pendiente y no como segundo estilo ya demostrado.

#### Validación

Tests del cálculo sin Gin/SQL, cliente con servidor HTTP de prueba, repositorio contra MySQL real y flujo desde Chromium hasta MySQL. Cobertura medida de application en la verificación final: 93,6%; no representa cobertura global del sistema.

#### Actualización 2026-11-08 - arquitectura base e integraciones

Se materializa Solar hexagonal: dominio y aplicación dependen de puertos Estimator/Supplier; HTTP y vendedor son adaptadores inyectados. Consumo mantiene capas. Motivo: aislar el contrato externo todavía desconocido y demostrar dos estilos reconocibles.

## Revisión vigente 2026-11-08 - contexto y justificación

**Estado:** Capas en Consumo y hexagonal en Solar implementadas.

### Contexto vigente

Consumo contiene reglas decimales estables que sirven tanto a web como a Clínica. Solar combina esas reglas con un vendedor cuyo contrato real aún no se recibió; necesitamos sustituir adaptadores sin reescribir el caso de uso.

### Decisión

Mantener Go/Gin; Consumo concentra cálculo en application y resuelve catálogo mediante interfaz. Solar separa dominio/aplicación/puertos Estimator y Supplier de adaptadores HTTP. La composición de dependencias ocurre en cmd/server.

### Por qué se elige para este proyecto

Reutilizamos el lenguaje y los límites por interfaces de los prácticos. Hexagonal es conveniente en Solar por la variabilidad de la integración. En el catálogo actual, la lectura HTTP → repository conserva SQL encapsulado sin añadir un Service que solo reenvíe llamadas: es más simple para las consultas sin reglas propias.

### Alternativas y comparación con clase

Una capa Service obligatoria y vacía, como adaptación mecánica de Controller → Service → Repository, añade indirección en esas lecturas. Omitir aplicación/puertos en Solar mezclaría validación comercial, HTTP y reglas. No se cambia la implementación existente para uniformar carpetas.

### Consecuencias, límites y evidencia

El catálogo tiene desacople menor que el ejemplo de repositorios por interfaz; si incorpora reglas de administración habrá que crear el caso de uso y su puerto. Las capas no equivalen a estilo solo por el nombre del directorio.

### Material que sustenta la decisión

Clase 2.pdf pp. 5-8; Clase 3.pdf pp. 12-16, 20-32.

**Qué cambió y por qué:** se explicitan contexto, criterio de elección y relación con los PDF prácticos a pedido del equipo; se conserva la tecnología/estilo previo y se distingue implementación de diseño pendiente. Las revisiones futuras se añaden a este mismo ADR, sin archivo de reemplazo.

## Actualización 2026-11-09 — Capas en Consumo y núcleo hexagonal en Solar

### Contexto y qué cambió

Consumo separa transporte, cálculo puro, resolver HTTP y repositorio SQL. Solar mantiene dominio sin infraestructura y aplicación con puertos Estimator/Supplier/ModelSupplier; RunStudy aplica selección y validación comercial. Adaptadores HTTP, Mongo y worker AMQP son externos al dominio. Usuarios usa adaptador HTTP/identidad/SQL.

### Decisión y por qué

El cálculo decimal se prueba sin bases; en Solar se sustituye el vendedor y se ensayan ofertas incompatibles sin alterar reglas. El worker coordina claim/persistencia y delega la selección en aplicación.

### Alternativas de clase y consecuencias

Clases1-3 y7. Se conserva Go y SQL explícito; no se introduce un ORM que oculte el límite transaccional.

### Estado y verificación

Código integrado en el entorno final local; el resultado de las comprobaciones y sus límites se registra en [VERIFICACION-FINAL](../VERIFICACION-FINAL.md) y [evidencias](../evidence/final-2026-11-09/README.md). Los estados pendientes de las revisiones anteriores no describen esta implementación. La publicación HTTPS y el contrato real del vendedor siguen siendo dependencias externas explícitas. Se actualiza este mismo archivo; no se crea un ADR de reemplazo.
