# ADR-006 - D6 - Búsqueda

> Vigencia: consultar la [revisión de 2026-11-08](#revision-vigente-20261108). Los estados anteriores se conservan como historia.

Versión 1.0.0 · Entrega 2 · Estado: **Adoptado para el hito; Meilisearch propuesto para la final**. Autores: Tiziano Nicolas y Francisco Skrie. Reemplaza: ninguna.

## Contexto

El catálogo necesita consultas verificables desde una primera base real. Todavía no existe mensajería ni un indexador durable.

## Decisión

En entrega 2 se consultan fichas activas en MySQL mediante nombre literal, categoría y modo; paginación de 20, máximo 100, página hasta 10000 y orden nombre/potencia con id de desempate. Los índices B-tree se crean con el esquema. Count y página comparten snapshot. Para la final se mantiene Meilisearch como proyección reconstruible desde MySQL, con eventos/outbox e índice de versión; atraso objetivo de 5 s saludable.

## Alternativas consideradas

Montar Meilisearch ahora sin sincronización reproducible agrega un índice inconsistente. LIKE es suficiente para seis semillas pero no resuelve relevancia ni full text. Un índice SQL FULLTEXT sería una alternativa intermedia.

## Consecuencias y validación

Se acepta recorrido de candidatos para búsquedas con comodín inicial. No se atribuye a esta entrega el requisito final de búsqueda indexada especializada. Las pruebas MySQL verifican escape de comodines, parámetros, paginación y exclusión de inactivos.

Las evidencias ejecutadas se enumeran en [DELIVERY-2](../DELIVERY-2.md). Una decisión propuesta no se presenta como una implementación validada.

## Revisión vigente 2026-11-08 - contexto y justificación

**Estado:** SQL LIKE actual; motor especializado pendiente.

### Contexto vigente

El catálogo actual tiene pocas fichas y filtros simples, pero el TP exige búsqueda por motor, paginación, filtros, orden y sincronización. SQL sigue siendo fuente de verdad.

### Decisión

Conservar Meilisearch como motor ya seleccionado en el diseño; aislarlo detrás de un puerto SearchEngine de Electrodomésticos. Configurar campos consultables, filtros y orden; proyectar versiones del catálogo y poder reconstruir. Retraso saludable objetivo <=5 s, todavía sin medición.

### Por qué se elige para este proyecto

La clase usa Solr. Para nuestro catálogo de nombres/categorías y consultas de interfaz, la API de documentos y configuración acotada de Meilisearch reduce el trabajo de preparar queries y ajustes frente a administrar schema/analyzers/eDisMax. Es una decisión de simplicidad operativa para este alcance, no una superioridad de relevancia o velocidad demostrada.

### Alternativas y comparación con clase

Solr es preferible si hacen falta analyzers específicos, ajuste avanzado de campos/boosts o consultas Lucene complejas. No lo sustituimos por LIKE: la búsqueda SQL actual no satisface el requisito. La idea de fuente canónica separada del índice y el puerto se toma del práctico.

### Consecuencias, límites y evidencia

Se renuncia al control avanzado de Solr que el práctico enseña. Habrá que validar calidad con consultas del dominio, filtros, paginación/orden y retraso real. No se afirma un benchmark entre motores ni se cambia la selección previa.

### Material que sustenta la decisión

Clase 6.pdf pp. 4-17, 23-30, 32; documentación primaria Meilisearch sobre filtros y configuración.

**Qué cambió y por qué:** se explicitan contexto, criterio de elección y relación con los PDF prácticos a pedido del equipo; se conserva la tecnología/estilo previo y se distingue implementación de diseño pendiente. Las revisiones futuras se añaden a este mismo ADR, sin archivo de reemplazo.

## Actualización 2026-11-09 — Meilisearch sincronizado y reconstruible

### Contexto y qué cambió

Se indexan fichas activas e inactivas con filtro activo, texto nombre/categoría, categoría/modo/potencia, orden y páginas. Outbox de catálogo provoca lectura canónica e indexación confirmada; invalidación de caché tras la tarea. Rebuild temporal y swap evita índice parcial. Objetivo sano de atraso5s; caída usa SQL degradado explícito.

### Decisión y por qué

El índice es derivado y no valida una evaluación. Conservar Meilisearch reduce integración para este catálogo acotado; Solr ofrece analizadores/control más amplios que este dominio todavía no requiere. No se afirma mayor rendimiento sin medición.

### Alternativas de clase y consecuencias

Clase6: índice separado, filtros, sort y reindexación. Se conserva la elección anterior y se acepta menor control de analyzers que Solr.

### Estado y verificación

Código integrado en el entorno final local; el resultado de las comprobaciones y sus límites se registra en [VERIFICACION-FINAL](../VERIFICACION-FINAL.md) y [evidencias](../evidence/final-2026-11-09/README.md). Los estados pendientes de las revisiones anteriores no describen esta implementación. La publicación HTTPS y el contrato real del vendedor siguen siendo dependencias externas explícitas. Se actualiza este mismo archivo; no se crea un ADR de reemplazo.


## Actualización 2026-11-09 — búsqueda de paneles solares para el cliente

**Contexto:** el usuario pidió que buscar/filtrar corresponda a paneles, manteniendo la arquitectura y el motor existente.

**Decisión y por qué:** Solar incorpora un índice paneles independiente en Meilisearch, con texto, potencia, superficie por unidad, moneda, precio, orden y páginas. La ficha Mongo sigue siendo canónica. Una marca pendiente se escribe atómicamente con la ficha; workers de ambas réplicas reclaman por lease y limpian la marca solo si sigue siendo la versión indexada. Se preserva el lease al editar para impedir que dos versiones del mismo panel se publiquen simultáneamente. Los errores conservan trabajo pendiente y se espera la confirmación de la tarea del motor. Una reconciliación cada minuto vuelve a configurar y sincronizar el índice para reparar pérdida del índice o resultados inciertos. Ante indisponibilidad se filtra sobre Mongo, sin inventar modelos.

**Alternativa y límites:** se conserva Meilisearch frente a Solr por la decisión previa y el alcance del práctico 6: fuente canónica separada, índice derivado, filtros/orden/paginación y reconstrucción. No se agregan contenedores ni se cambia el dominio de recomendación. El API/índice de equipos se conserva para compatibilidad y lectura del selector de equipos; su buscador se retira de la interfaz. No se compara precio entre monedas ni se interpreta precio desconocido como gratis. La lectura del índice es eventual; el cálculo comercial sigue consultando Mongo canónico.

**Evidencia:** pruebas unitarias de filtros/límites y respaldo; HTTP real exige indexación saludable <5 s, comprueba la última de varias ediciones y retira una ficha inactiva. Prueba de escritorio/móvil verifica búsqueda y datos técnicos solo dentro de la ficha. Ver docs/EXPERIENCIA-CLIENTE.md y contrato panel-search-v1 1.0.0.
